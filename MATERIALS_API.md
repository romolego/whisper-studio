# Материалы проекта: интерфейс и работа агента

Резюме, протокол и варианты схем привязаны к ID проекта. Интерфейс и агент
используют одинаковый HTTP API; клики в браузере для пакетной обработки не нужны.
API доступен на `http://127.0.0.1:8765`, интерактивная схема — `/docs`.
Генерация во внешней LLM остаётся задачей пользователя или агента: сервис сам
не отправляет транскрибации во внешние модели.

## Рабочий цикл агента

1. Найти проекты через `GET /api/projects` или
   `GET /api/materials/status?folder_id=<ID>`. Второй маршрут возвращает все
   проекты указанной папки, включая скрытые из общей ленты, с полями
   `transcription_ready`, `summary_ready`, `minutes_ready`, `diagram_count`,
   `revision`. Без `folder_id` — все проекты. Не создавать повторные материалы,
   если они уже заполнены, без указания пользователя.
2. Дождаться готовой транскрибации, используя существующий API заданий/очереди.
3. `GET /api/projects/<ID>/materials/prompt/summary` возвращает `prompt`,
   `transcript` и готовый `input` для LLM. Виды: `summary`, `minutes`, `diagram`.
   Параметры `timestamps=none|segments|words`, `formatting=formatted|plain`,
   `speakers=off|on`, `speaker_keys` — те же, что у API просмотра транскрибации.
   По умолчанию: без таймкодов, с пунктуацией, без спикеров. Они задаются явно
   и не зависят от предыдущих экспортов или открытого браузера.
   `include_transcript=false` даёт только промпт. Если готового текста нет,
   запрос с транскрибацией вернёт 409.
   Для схемы `include_materials=true` добавляет заполненные резюме и протокол:
   промпт → резюме (если есть) → цифровой протокол (если есть) → исходная
   транскрибация. Между блоками — разделители и явные заголовки. Тексты материалов
   берутся из этого проекта; ответ содержит также `materials_revision`.
4. Обработать `input` в разрешённой пользователем модели. Не менять промпт:
   предустановки хранятся в `app/transcript-prompts.json`, актуальный пользовательский
   каталог доступен через `GET /api/material-prompts`.
5. Получить `GET /api/projects/<ID>/materials`; сохранить результат запросом
   `PUT /api/projects/<ID>/materials/text/summary` (или `minutes`):

   ```json
   {"text": "Результат обработки", "revision": 0}
   ```

   Ответ — полное актуальное состояние с новой `revision`. Повторная запись
   того же текста идемпотентна: после потери ответа её можно повторить со старой
   ревизией, если текст на сервере уже совпадает. Другие материалы не меняются.
   Использовать возвращённую
   ревизию для следующей записи. Текст сохраняется буквально, включая Markdown
   и переносы. Word поддерживает заголовки, жирный текст и маркированные списки.
6. Для схем: `POST /api/projects/<ID>/materials/images`, multipart-поля
   `file` и `revision`. Поддерживаются PNG/JPEG/WebP. Искусственных лимитов размера, разрешения
   и количества нет; загрузка копируется на диск потоком. Файлы проверяются декодированием, байты не изменяются.
   Ответ содержит ID каждой картинки.
7. `PUT /api/projects/<ID>/materials/images` принимает текущую ревизию и
   **полный** упорядоченный список `images: [{"id": "...", "note": "..."}]`.
   Пропущенные существующие ID удаляются; новые и повторяющиеся ID запрещены.
   Сначала прочитать список, затем менять порядок/примечания/состав.

Разные проекты можно обрабатывать параллельно. Внутри одного проекта записи
последовательны: ревизия общая для текста и картинок. HTTP **409 при записи**
означает конфликт с другим агентом или человеком: прочитать актуальное состояние,
сравнить изменения и согласовать их, а не повторять запись со свежей ревизией
вслепую. HTTP 400/422 — неверные данные или лимит, 404 — нет проекта/материала.

## Экспорт одного проекта

- `GET /api/projects/<ID>/materials/text/summary/docx` (также `minutes`, `txt`).
- `GET /api/projects/<ID>/materials/images/<IMAGE_ID>?download=true`.
- `GET /api/projects/<ID>/materials/package/zip?include_transcript=true&transcript_format=txt`.
- `/package/files` с теми же параметрами возвращает снимок файлов как JSON
  `{"files":[{"name":"Резюме.docx","base64":"..."}]}`. Это позволяет получить
  несколько отдельных файлов без нескольких изменяющихся между запросами снимков.

Пакет содержит заполненные резюме/протокол в Word, все схемы в текущем порядке,
примечания отдельным TXT и, если включено, объединённую транскрибацию проекта.
Параметры вида транскрибации те же, что в шаге 3. Для пустого проекта пакет не
создаётся. Если материалов несколько, каждый сохраняется отдельным файлом.

## Массовое сохранение на диске

`POST /api/materials/export`:

```json
{
  "folder_id": "ID_ПАПКИ",
  "mode": "both",
  "include_transcript": true,
  "transcript_format": "txt",
  "timestamps": "none",
  "formatting": "formatted",
  "speakers": "off"
}
```

Вместо `folder_id` можно передать `project_ids: ["ID1", "ID2"]` (до 500).
Нужно ровно одно из двух полей. Режимы: `files`, `zip`, `both`.
Если параметры включения и формата транскрибации опущены, используются настройки
`materials_include_transcript` (по умолчанию `on`) и
`materials_transcript_format` (по умолчанию `txt`).

Результат сохраняется в `data/material-exports/<export_id>/`. Для каждого проекта
создаётся папка с названием и полным ID, отдельными файлами и/или ZIP.
Ответ содержит абсолютный `directory`, список `projects` с путями `files`,
список `errors` для пропущенных/пустых проектов и `download_url` общего архива.
Ошибки отдельных проектов не скрываются и не останавливают остальные.
В каталоге также лежат `Отчёт.json` и общий `Пакет.zip`.
Агент должен проверить `errors` и наличие файлов перед отчётом об успехе.
Архив можно скачать через возвращённый URL. Копирование в другой пользовательский
каталог выполняется агентом отдельно, в рамках запроса пользователя.

## Хранение и перенос на другую платформу

`backend/materials.py` — хранилище и операции с материалами,
`backend/material_exports.py` — сборка массовых экспортов,
`backend/materials_api.py` — HTTP-граница. UI использует только API.
Сейчас источник истины — `<папка проекта>/materials/materials.json` с
`schema_version`, `revision`, `updated_at`, текстами и упорядоченными вложениями.
Рядом автоматически создаются `Резюме.txt/.docx`, `Протокол.txt/.docx`, а оригиналы
схем лежат в `images/`. Переименование/перемещение проекта сохраняет материалы.
Не править JSON/экспортные файлы напрямую: использовать API и ревизии.
Запись, переименование и удаление проекта используют общую блокировку.
После прерывания записи TXT/Word восстанавливаются из последнего зафиксированного
JSON. Повреждённый JSON не заменяется пустыми данными: API возвращает 503.
Частичные файлы не включаются в массовый ZIP, итоговый архив публикуется атомарно.

При переносе на Эталон следует заменить адаптер хранения: проект соответствует
объекту, тексты — его данным, схемы — вложениям. Сохранять контракт API и проверку
ревизий транзакцией платформы. Текущий файловый адаптер рассчитан на один процесс
локального API (параллельные клиенты поддерживаются); для нескольких серверных
процессов нужен общий транзакционный адаптер. Сам перенос на Эталон здесь не выполнен.

В интерфейсе текст и примечания сохраняются после короткой паузы и при закрытии
окошка. До подтверждения сервера черновик текста/примечаний хранится в localStorage
этой вкладки браузера (ключ включает API, проект и идентификатор редактора).
Верхняя панель и блок «Материалы по транскрибации» используют общий клиентский
store и одну очередь записи по проекту. Поздние ответы чтения не откатывают
подтверждённые изменения. Ошибка отображается, при конфликте автоматическая перезапись
останавливается. «Загрузить серверный вариант» предварительно скачивает черновик,
если есть несохранённые изменения. Картинки сначала должны полностью загрузиться;
закрытие вкладки во время их загрузки не гарантирует сохранения незавершённого файла.
Новые данные/экспорты приватны и находятся в игнорируемом `data/`.
Если готовой транскрибации ещё нет, пакет содержит только доступные материалы.
Если готовая транскрибация есть, но выбранный фильтр даёт пустой текст,
пакет вернёт ошибку вместо молчаливого исключения запрошенного исходника.

Каждый раздел верхней панели независимо запоминает вкладку внутри текущего
проекта в localStorage браузера, включая перезагрузку страницы и перезапуск сервиса;
первое открытие раздела показывает промпт. В режиме чтения текст
отображается как Markdown, исходная разметка остаётся в редакторе и TXT.
Word/TXT доступны после выхода из правки. Пояснение к пакету скрыто под «?».

Схему можно бросить на кнопку «Схема» или в любую часть её окошка, включая
промпт. Порядок меняется перетаскиванием карточек; одиночная схема занимает
всю ширину. Просмотр поддерживает листание стрелками, закрытие по фону и Escape.
При выборе через файловый диалог список файлов копируется до асинхронного
обновления материалов: очистка поля выбора не отменяет уже выбранные схемы.
`POST /api/projects/<ID>/materials/reveal` открывает папку материалов в проводнике.

## Настраиваемые промпты

В «Настройки → Промпты и материалы» можно включить весь блок, изменить текст и
название кнопок, включить/выключить, удалить или переместить любую кнопку и
добавить собственную: `text` (текст) или `images` (картинки). Тип после создания
не меняется, в том числе у трёх предустановленных кнопок. Удаление или выключение
кнопки не удаляет сохранённые материалы; они остаются в проекте и экспорте.

`GET /api/material-prompt-settings` возвращает `{revision, enabled, prompts}`.
`PUT` на тот же адрес принимает полный упорядоченный список с текущей ревизией.
Каждый элемент: `{id, label, title, text, type, enabled}`. ID своих кнопок имеет
формат `custom_` + 32 hex-символа. Повтор одинаковой записи идемпотентен;
конфликт ревизии — 409. Настройки хранятся в игнорируемом `data/prompt-catalog.json`.
GET без настроек возвращает предустановки и ничего не записывает на диск.

Старые маршруты и поля `summary`, `minutes`, `images` сохраняются. Текст своей
кнопки записывается через `/materials/text/<custom_ID>`; ответ дополнительно
содержит `texts: {custom_ID: text}` и `definitions: {custom_ID: {label,type}}`.
Картинки загружаются через `/materials/images?kind=<custom_ID>` и имеют
`prompt_id`; без него это прежняя «Схема». Список PUT images остаётся полным
списком проекта, включая остальные группы. Ревизия одна для всех материалов.
Настроечный редактор хранит неотправленные правки в браузере и при конфликте
останавливает перезапись; загрузка серверного варианта предварительно скачивает
черновик. ZIP одного проекта получает имя проекта; содержимое дополнено всеми
собственными текстами и группами картинок, включая результаты удалённых кнопок.

Черновик настроек привязан к API и идентификатору редактора в sessionStorage;
старый общий черновик переносится в текущую вкладку перед удалением старого ключа.
Неудачный GET не удаляет черновик, поздний GET не заменяет введённую за время
загрузки правку. Совпадение содержимого с сервером снимает ложный конфликт после
потери подтверждения записи. Реальное различие версий по-прежнему требует сверки.

В интерфейсе переключатели сохраняются автоматически. Карандаш у промпта
открывает режим правки; перемещение и удаление доступны только внутри него.
Добавление и правка названия/текста/позиции работают с отдельной копией в диалоговом
окне: до подтверждения она не меняет каталог, его локальный checkpoint или
сохранённые материалы. «Отмена», Escape, крестик и клик вне окна отменяют эту
правку. «Готово» доступно при изменениях существующего промпта, «Сохранить»
при добавлении появляется после заполнения названия и текста. Подтверждение
использует прежнюю очередь PUT с проверкой ревизии и защитой черновика при сбое.

Экспорт уже сохранённого собственного текста использует `definitions` проекта:
повреждение общего каталога промптов не блокирует чтение и пакетный экспорт
материалов. Имя такого файла соответствует сохранённому снимку проекта.
При восстановлении после прерванной первой записи очищаются только служебные
`Текст.txt/.docx` незарегистрированного собственного материала; другие файлы
в его каталоге не удаляются, внешние ссылки не обходятся.
